## L01 · 横屏宝物说明裁切（P2）

**复现。** 上述固定种子横屏新开局，停在“这次带哪件宝物”。三个候选为“同色也翻倍”“断一次不算”“凑白×8”。实际只露说明首行：第一件缺“翻倍。”，第二件缺“没反应，算作顺色。”，第三件缺“（原来×5）。”。本机龙奖励页的“慢一拍”等也发生裁切。

要复现龙奖励：设置→“门厅 第6间”→再次打开设置，把“设怪的血”设为0→关闭设置→结束回合，停在真实奖励页。不要用“第一幕去留”验证奖励页；该快捷入口会自动击杀龙并领取宝物。

**代码定位与要求。** `scripts/app/game.gd::_relic_pick()` 组合固定卡框、图标、名称与说明区域，说明有clip和三行上限；横屏留给说明的有效高度不足。修复应让完整效果可读，兼容长名字、长说明、选中后放大/上移及未选中状态；不删文案、不改效果、不把完整说明藏进用户无法发现的开发入口。竖屏目前这些候选的说明可读，仍需回归。

**解除证据。** 横竖屏各交开局与龙奖励实际GPU图，至少覆盖未选中和选中放大；逐字核对完整文案、提示和“拿这件”按钮。节点存在或Label.text正确不能证明未裁切。

## L02 · 去留/收藏标题被面板盖住（P2，收藏标题P3）

**复现。** 横屏设置→“第一幕去留”，内容面板盖住“带走，还是继续？”标题，仅剩横幅上缘装饰。第二幕第6间→设怪血0→结束回合→选择并领取宝物，第二幕去留页同样盖住“长廊已过”。首页→收藏室，收藏面板盖住“收藏室”横幅，但“已收藏6/15”仍可见。

**代码定位与要求。** `_act_choice()`、`_collection()` 先画banner后画 `layout.result.panel`，横屏两者区域重叠。为标题和有效内容分别安排不相交区域，兼容所有页面与两方向。不能只把横幅提高z-index而继续让它压住内容；那会留下L03。

**解除证据。** 重截横竖屏两种去留与收藏页，确认标题完整、选项/选中反馈/确认按钮可读可操作，收藏滚动到底不被底栏遮挡。旧图证明缺陷存在，不能当修复后证据。

## L03 · 结算置顶横幅压住正文（P2）

**复现。** 横屏进入带走或失败结算，顶部“带着宝物回家”/“失败”横幅压住面板第一行老门环文案；失败页还压住“倒在第1仗·布偶熊”等标题上缘。结算滚动时，滚入同一区域的条目仍被横幅遮挡。

带走可经两幕龙奖励后的去留选择生成。失败可在自然战斗设置“设心”为1、“设倒计时”为0，关闭设置后结束回合。不要把debug生成的结算当自然完整通关。

**代码定位与要求。** `_result()` 的 `ResultBanner.z_index=20` 与 `ResultScroll` 的内容起点占用同一区域。修复须为横幅保留独立空间，或者调整实际可视滚动区域；保证初始顶部与任意滚动位置均可读。不能靠隐藏老门环文案或减少结算字段消除问题。

**解除证据。** 带走、失败两方向均交顶部与滚动末端的真实图，检查完整文案、最远记录、宝物/新收藏行、回首页及再来一局按钮；检查连点、滚动、回首页后的清理。底栏按钮在原图完整，不应因修顶部产生新遮挡。

## L04 · 限六张常驻提示被剩余手牌挡住（P2）

**复现。** 隔离的新局领取开局宝物后：设置→“长廊 第3间”→设置“发指定的牌”填 `1,1,1,1,1,2,2`→连续按数字键1打出6张。场上剩一张绿牌。常驻“这回合打满6张了”被中央剩余手牌挡住，只露末尾；尝试第7张时的临时拒绝提示可见，规则本身正确拒绝。

自然永久牌组有5红、5绿，因此这个7牌序列无需补造新ID。修复前本机读取的两份six存档均为 `act=2,room=3,row=6,hand=[2],nextCardId=31`，尝试前后字节一致；这一条是有效状态证据，不能与L05的旧快照混淆。它不证明完整真实触屏/拖放体验通过。

**代码定位与要求。** `_hand()` 把 `SixCardLimit` 放在 `layout.loot.hint`，与动态手牌区域冲突。应给常驻限制信息可靠的可视区域，覆盖横竖屏、手牌张数变化及撤回后的重新布局；不得删除提示或放宽限六张规则。

**解除证据。** 六张后分别用鼠标、数字键和拖牌尝试第7张，现场和有效磁盘均不变，无虚构伤害预览；按Z后五张桌牌/两张手牌恢复可出，提示随状态正确更新。限六张已打穿、封条第6张与第7张等旧规则用例继续保留。至少交两方向六张限制图，提示与剩余牌完整可见。

## L05 · debug补造新牌未推进身份计数器，保存拒绝（P2）

**复现。** 使用全新隔离目录，新开局领取宝物，先核对真实磁盘 `gemcard.run.json` 是合法30牌、`nextCardId=31` 的自然战斗。设置→“发指定的牌”，填 `1,potion,palette,diamond`。UI出现四张指定牌且可以出牌、回血、撤回，但磁盘仍停在先前随机手牌。

**确定根因。** `game.gd::debug_deal(sequence,test=0)` 从永久牌组取牌，找不到时以局部 `identity=max(已有id)` 再递增，且确实把新牌加入 `run_state.cards`；它没有更新 `run_state.nextCardId`。于是永久牌组33张、新增ID31/32/33而nextCardId仍31。`rules/save_state.gd::_v5_details()` 要求每张 `card.id < nextCardId`，`Save.encode_run_save()` 返回null并报告“不能保存不完整的一局”；`Persistence.save_run()` 返回false，保留原磁盘档。

`Game._persist()` 只调用 `_storage_warning()`，不输出ERROR；`save_warning_shown` 整个进程只提示一次，`_reset()` 不重置它。因此日志没有ERROR或之后没有toast，都不能证明保存成功。

独立原生节点诊断已经得到以下结果，供远端重新实现最小复现，不要求远端拥有本机artifacts：

```json
{
  "kind": "known_defect_reproduction",
  "acceptanceResult": "NOT_PASS_KNOWN_DEFECT",
  "baseline": {"cardCount": 30, "nextCardId": 31},
  "afterDebugDeal": {"cardCount": 33, "newIds": [31, 32, 33], "nextCardId": 31},
  "encodeReturnedNull": true,
  "storageSaveReturned": false,
  "storageLastError": "不能保存不完整的一局",
  "diskBytesUnchanged": true,
  "control": {"nextCardId": 34, "saveSucceeded": true, "reloadSummaryMatchesLive": true}
}
```

对照是在另一新局先调用既有 `R.debug_give_tool` 各添加一张药水、调色盘、钻石；该入口调用 `R.next_identity(state)` 合法推进至34，再指定同一手牌即可保存并读回。这个对照没有修复生产代码。诊断进程退出0表示成功复现预期缺陷，不属于5277项通过，也不是产品验收通过。

**修复要求。** 补造牌统一使用合法身份分配，保持 `cards` 与战斗各牌区的ID守恒、唯一性及 `nextCardId>全部已用id`；保留工具上限和非法输入不变性。不放宽Save白名单、不删除校验、不把debug状态偷偷当练习、不吞掉保存失败。已有牌复用、补多张、曾消费药水导致ID有空洞、重复发牌均须正确。

**必须新增的回归。** 按 `tests/test_batch_two_ui.gd` 的原生Game节点模式或等价真实UI入口，用独立SAVE_DIR建立自然合法战斗，再直接调用 `app.debug_deal([1,"potion","palette","diamond"])`。核对现场新ID/nextCardId、编码结果、storage.last_error及真实文件内容；销毁并新建Game或持久化实例读回，比较规范化数字后的牌ID/类型/次序、永久牌组及当前阶段。继续出药水、撤回、重打、提交回合和重启恢复，确认不能重复消费或返还永久牌堆。不能只测纯规则给牌助手，那样会绕过这次缺陷。

**证据界限。** 原本机 `potion-played.json`、`potion-undone.json`、`new-cards-before-commit.json`、`new-cards-after-commit.json` 是采样时读取到的旧磁盘快照：30牌、随机7手牌、row=0；不能用它们证明新牌现场状态、药水消费或重启恢复。修复后必须重新采样并先核对内容，不仅比较文件名或前后相同。
