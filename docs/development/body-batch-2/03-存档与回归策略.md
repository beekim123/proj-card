# 本体第2批 · 存档、结算与回归

## 1 存储合同

当前活动局格式是 `{"version":4,"state":...}`，文件名 `gemcard.run.json`。本批新写v5；保留精确JSON数值解析，不改成宽容浮点误差比较。新增阶段/牌/怪/宝物、药水标记、奖励去向都进入严格校验。

v5至少增加本局唯一 `runId`、内容版本、宝物奖励去向，并允许 `act_choice` 活动状态。`act/room/fight`、所属幕怪池、龙规则、合法门奖励、牌ID守恒、持有数量、撤回快照和药水消耗要相互验证，不能只检查字段类型。

特别修正现有校验假设：

- `fight`、`monsters` 不能继续限制为6间；既有 `stats.fights` 要允许12仗并保持顺序。
- `phase=relic` 的候选数由当前奖励池算；初始收藏池≠全15件池。
- 本批可在药水消耗后少于20张牌；不能继续无条件拒绝少于 `shop.minDeck` 的合法局。
- 龙后宝物与去留阶段还引用最后一仗怪，但不能被当成已结束、不能过早删除存档。
- `hist` 需要恢复心数和药水标记；所有引用白名单含新内容，拒绝未知key和伪造的第三幕/加码。

## 2 v4旧局处理

接收方先保存v4原文备份，再按v4原有规则验证；**验证旧局时使用冻结的第一幕/9牌/10宝物配置**，不能用已扩成两幕的v5配置要求它有12个怪。

合法v4活动局迁成v5，保留当前幕/间、手牌、牌序、当前奖励候选、心、成长、撤回、统计和RNG。第二幕未进入的房间可延迟生成，不为迁移提前消耗当前局RNG。当前开局的3个候选照留，即使其中尚未收藏；仅本次旧局适用，下次新开局从收藏池抽。

旧局里拿到但未带出的宝物不自动计入收藏；只有以后成功带走才入收藏。迁移后的第一幕龙结束可继续到第二幕。旧版本已完成的6仗胜利纪录不能反向授予收藏或完整三幕通关。

v4无runId，迁移时由存储适配器一次性注入并持久化；反复重开必须得到同一迁移局身份，不重复创建。迁移写失败不覆盖或清除旧档，保留可恢复原文并展示存储提示。原有更早版本的过期策略可沿用；未知更新版本不覆盖其原始文件，提示版本不支持。损坏档保存诊断备份后按原有错误流程处理，不悄悄重置正常收藏。

## 3 收藏与纪录原子结算

当前 `persistence.gd` 已有临时文件＋rename、`clearedRun` 回执、保存generation保护。扩展此协议，不重新做一条“先写收藏再写纪录”的双写流程。

推荐 `gemcard.records.json` 新外壳为：

```json
{
  "version": 2,
  "records": {"played": 0, "wins": 0, "farthest": 0, "bestTurn": 0, "maxOverkill": 0, "retreats": 0},
  "profile": {"version": 1, "collected": ["same", "once", "white", "rainbow", "heart", "grow"]},
  "settledRunIds": [],
  "clearedRun": null
}
```

外壳字段可按实现增补，但这些语义必须成立：

1. 纯规则先算下一份纪录和收藏；存储一次原子rename提交二者及本局回执。
2. 成功后才更新内存中的“已领取”标记，并尝试清掉本局活动档；删除失败时回执保证重启不重发。
3. 写失败则内存、收藏、纪录不算已提交；UI允许重试，不能显示已解锁而磁盘没有。
4. 同runId重复结算、反复打开结果、读到旧活动档，都只计一次；不同runId即使同seed仍是不同旅程。
5. 旧局迟到回调不得清理或改写新局存档，延续现有ownership/generation保护。已存在的回执不能因普通 `save_records` 丢失。
6. 初始收藏只在第一次无档时建立；同一文件损坏、IO失败和不存在必须区分，不能用默认值覆盖正常收藏。

旧平铺纪录可迁入records子对象，保留已有成绩；`retreats` 从0起。`played` 对本批每次带走/失败/放弃只加1；`wins` 不因本批带走增加，旧值作为旧旅程成绩保留，不能显示成“三幕通关次数”。第3批再加入明确的完整通关指标。`farthest` 扩到12仗；旧完成值7按“门厅已过”映射，不能显示为已打进第二幕。去留阶段属于本局尚未结算，不提前加played或retreats。

## 4 测试数据的版本边界

本批开始先运行完整 `tools/check.sh`，保存当前基线结果。当前历史数为4866项，含377个H5命名用例、312条黄金轨迹和400条历史轨迹；这些证明v4移植，不证明尚未开发的v5两幕功能。

`h5/`、`tests/h5-fingerprints.json` 和旧oracle/golden原始数据保持不变。新内容会有意改变新开局候选、房间数、存档和结算，不能要求v5默认输出仍与v4完整状态逐字相同，也不能删除旧失败用例来宣称全部通过。

实施时分清：

- 未改规则的算数、随机数、原牌效果、布局、音效/素材与基础文件语义回归继续运行。
- v4格式与v4样本用于原验证器、迁移测试或明确隔离的历史回放；必要时从已推送的Godot基线取原行为作比较，不复制整个旧游戏进生产代码。
- 对因为本批设计而变化的集成用例，在 `docs/v2/batch-2-test-migration.md` 逐项列旧入口、变化原因、新断言、新入口和仍保留的历史样本；新runner必须运行相应替代测试。没有解释的失败必须修复。
- 新规矩、收藏、跨幕、药水撤回用人工可计算预期作独立断言；可以增加v5黄金轨迹，但不能只用被测实现生成自己验证自己的答案。

固定种子对局至少100局完整两幕命令回放；覆盖带走、继续、失败、放弃、各奖励和各规矩，并证明保存恢复前后下一步/RNG一致。它用于流程与不变量，不声称等同真人平衡性验收。现有全局计算预算下按1worker顺序执行，不启动原模拟器的4进程入口。
